## 1. Что мы строим

SaaS для самозанятых монтажников (первая ниша — кондиционеры).
Ключевой сценарий: монтажник на объекте диктует позиции голосом или текстом
(«монтаж девятки, трасса 4 метра, штроба бетон 2 метра, помпа») →
ИИ распознаёт позиции → подставляет цены из личного прайса пользователя →
через минуту готовые PDF: смета, договор, акт с логотипом и реквизитами
пользователя → отправка клиенту ссылкой, клиент согласовывает онлайн.

Модель: подписка. Free (3 документа/мес, водяной знак) / Pro 790 ₽/мес
(безлимит, свой бренд) / позже Бизнес 1590 ₽ (CRM-функции).

Владелец проекта — практикующий монтажник (Хабаровск), он же пользователь №1.
Все продуктовые решения проверяются вопросом: «поможет ли это монтажнику
закрыть сделку быстрее?»

## 2. Принципы разработки (нарушать нельзя)

1. **MVP-дисциплина.** Реализуем ТОЛЬКО то, что в разделе «Scope MVP».
   Любая идея сверх — записывается в `docs/backlog.md`, НЕ в код.
2. **Простота > элегантность.** Никаких микросервисов, очередей, Kubernetes.
   Монолит FastAPI + Postgres + Docker Compose. Рефакторинг ради красоты
   запрещён до 100 активных пользователей.
3. **Масштабирование закладываем архитектурой, не инфраструктурой:**
   - весь код stateless (сессии и файлы — не в памяти процесса);
   - файлы (логотипы, PDF) — в S3-совместимое хранилище через абстракцию
     `app/storage.py`, локально — MinIO;
   - конфигурация только через переменные окружения (12-factor);
   - БД сразу Postgres (не SQLite), миграции только через Alembic;
   - мультиниша заложена в данных: справочники позиций — записи в БД
     с полем `niche` (hvac / plumbing / electric), не хардкод.
4. **Каждая фича — вертикальный срез:** модель → API → UI → тест.
   Не строим «весь бэкенд, потом весь фронт».
5. **Безопасность по умолчанию:** пароли/коды — только хэши, секреты — только
   в env, PDF-ссылки клиентам — неугадываемые UUID + срок жизни,
   персональные данные (ИНН, реквизиты) не пишем в логи.
6. **Деньги — священны.** Код оплаты (ЮKassa) покрывается тестами в первую
   очередь. Вебхуки идемпотентны: повторная доставка не создаёт дубль подписки.

## 3. Стек (зафиксирован)

- Backend: Python 3.12, FastAPI, SQLAlchemy 2.x, Alembic, Pydantic v2
- БД: PostgreSQL 16
- Frontend: PWA — Vue 3 + Vite (или предложи проще, но SPA + manifest + offline-заглушка обязательны)
- PDF: WeasyPrint (HTML-шаблоны → PDF), шаблоны в `app/templates/pdf/`
- ИИ-парсинг: Anthropic API (модель claude-sonnet, промпты в `app/prompts/`)
- Голос: Web Speech API в браузере; фолбэк — текстовый ввод (серверное STT — в backlog)
- Платежи: ЮKassa (подписки, вебхуки)
- Инфраструктура: Docker Compose, nginx, certbot; хранилище — MinIO/S3
- Тесты: pytest + httpx; фронт — минимум smoke-тестов

## 5. Модель данных (ядро)

- `users`: id, phone (уникальный), created_at, role
- `profiles`: user_id, brand_name, full_name, inn, requisites(jsonb), logo_key, signature_key
- `price_items`: id, user_id, niche, name, synonyms(text[]), unit, price, sort
- `documents`: id, user_id, type(estimate|contract|act), status(draft|sent|approved),
  payload(jsonb — позиции, суммы), pdf_key, public_uuid, expires_at, parent_id
  (у договора/акта parent_id → смета), created_at
- `subscriptions`: user_id, plan(free|pro|business), status, period_end,
  yookassa_payment_method_id
- `usage_counters`: user_id, month, documents_created  # лимиты Free
- `parse_logs`: id, user_id, raw_input, parsed_json, corrected_json, created_at
  # каждая правка пользователя — материал для улучшения промпта

Правило: payload документов — снапшот. Изменение прайса задним числом
не меняет уже созданные документы.

## 6. Scope MVP (и ничего больше)

1. Вход по номеру телефона + SMS-код (провайдер за абстракцией `services/sms.py`)
2. Профиль: бренд, ФИО, ИНН, реквизиты, логотип, подпись
3. Прайс-лист: CRUD позиций + предзаполненный шаблон «кондиционерщик»
4. Парсинг: текст → JSON позиций → экран проверки/правки → подтверждение
5. Смета: PDF на бланке пользователя + публичная ссылка с кнопкой «Согласовать»
6. Договор и акт одной кнопкой из сметы
7. История документов, дублирование сметы
8. Биллинг: Free-лимит 3 док/мес + водяной знак; Pro 790 ₽ автосписанием; экран пейволла
9. Онбординг: 3 экрана до первой сметы
10. Админ-минимум: список юзеров, метрики (регистрации, документы, конверсия) —
    можно простым /admin с basic auth

Явно ВНЕ MVP (в backlog): нативные приложения, TG Mini App, расписание,
GPS, склад, 1С, серверное распознавание речи, мультипользовательские бригады,
онлайн-оплата смет клиентами.

## 7. Окружения и деплой

Три окружения:

| Окружение | Где | Ветка | БД | Назначение |
|---|---|---|---|---|
| dev | локально, docker compose | feature/* | локальный Postgres | разработка |
| staging | VPS, стек staging | main | своя БД (тест-данные + обезличенный слепок прода) | проверка обновлений |
| prod | VPS, стек prod | тег release-* | боевая БД | пользователи |

Правила деплоя:
1. **Ничего не попадает в prod, минуя staging.** Без исключений, включая «однострочные фиксы».
2. Пайплайн: PR → тесты зелёные → merge в main → автодеплой на staging →
   ручная проверка чек-листа → тег release-X.Y.Z → деплой на prod.
3. Чек-лист staging перед релизом (хранится в docs/runbook.md):
   регистрация нового юзера · создание сметы через парсер · PDF открывается ·
   публичная ссылка работает · договор+акт генерируются · тестовый платёж
   ЮKassa (тестовый магазин) проходит · вебхук обработан · лимит Free срабатывает.
4. Миграции БД: только аддитивные в один релиз (сначала добавили колонку —
   следующим релизом удалили старую). Перед миграцией на prod — автоматический
   дамп БД. Каждая миграция имеет downgrade.
5. Откат: `docs/runbook.md` содержит команду отката на предыдущий образ
   (docker image с тегом прошлого релиза хранится всегда) + восстановление дампа.
   Цель: откат за 5 минут одной командой.
6. Образы собираются один раз и промоутятся: тот же образ, что тестировался
   на staging, едет в prod (никакой пересборки «по пути»).
7. Секреты prod и staging разные (отдельные .env на серверах, в git не попадают).
   ЮKassa: staging — тестовый магазин, prod — боевой.

## 8. Наблюдаемость

- Логи: structlog, JSON, без персональных данных; docker logs + ротация
- Uptime и алерты: healthcheck-эндпоинт /health (проверяет БД и хранилище),
  внешний пинг с уведомлением в Telegram владельцу
- Бэкапы: pg_dump ежедневно → S3/отдельное хранилище, хранение 30 дней,
  еженедельная автоматическая проверка восстановления на staging
- Sentry (или аналог) для ошибок backend и frontend — с первого дня staging

## 9. Стиль работы Claude Code в этом проекте

1. Перед задачей: прочитай CLAUDE.md и docs/decisions.md, скажи в 2–3 строки
   план, потом делай.
2. Одна задача = одна ветка = один PR. Коммиты небольшие, сообщения по-русски,
   формат: `тип: что сделано` (feat/fix/chore/docs/test).
3. Пиши тесты на: парсер (датасет диктовок → ожидаемый JSON), лимиты Free,
   вебхуки ЮKassa, генерацию PDF (смок: файл создаётся, ключевые поля на месте).
4. Если требование неясно — задай вопрос, не придумывай. Если видишь, что
   задача тянет фичу вне Scope MVP — останови и предложи запись в backlog.
5. Любое архитектурное решение (новая библиотека, изменение схемы БД) —
   1 абзац в docs/decisions.md: дата, что решили, почему.
6. Не трогай без явной команды: схему биллинга, публичные URL документов,
   формат parse_logs.
7. Русский язык во всех пользовательских текстах, комментариях и документации.
   Названия переменных/функций — английские.
